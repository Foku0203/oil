Amazon Elastic Block Store (Amazon EBS)

=== P011
# Amazon EBS
Amazon EBS volumes:
- ต่อผ่านเครือข่าย (Network-attached)
- เป็นพื้นที่จัดเก็บแบบบล็อกที่คงอยู่ถาวร (Persistent block storage)
- รองรับทั้ง boot volume และ data volume
แผนภาพ: AWS Cloud → Region → Availability Zone: Instance 1 และ Instance 2 บน VM host computer เชื่อมกับ Amazon EBS volume

=== P012
# ประเภทของ Amazon EBS volume
**Solid State Drives (SSD):**
- Provisioned IOPS SSD (io1) volumes
- General Purpose SSD (gp2) volumes
**Hard Disk Drives (HDD):**
- Throughput Optimized HDD (st1) volumes
- Cold HDD (sc1) volumes

=== P013
# สร้าง Amazon EBS volume
- volume อยู่ภายใน Availability Zone หนึ่ง
- ตัวอย่าง AWS Command Line Interface (AWS CLI):
  - ใช้คำสั่ง create-volume
  - ใช้ตัวเลือก `–-availability-zone` เพื่อระบุ Availability Zone
```
$ aws ec2 create-volume –-size 80 \
–-availability-zone us-east-1a --volume-type gp2
```

=== P014
# ดูรายละเอียดของ volume ที่เพิ่งสร้าง
คำสั่ง CLI สำหรับดูรายละเอียดของ volume ที่สร้าง:
```
$ aws ec2 describe-volumes --volume-ids vol-0e5e5193f8d093d5f
```

=== P015
# ต่อ (attach) Amazon EBS volume
- ต่อ volumes เข้ากับจุดเมานต์เชิงตรรกะ (logical mount points) ในระบบปฏิบัติการ
- ตัวอย่าง AWS CLI:
  - ใช้คำสั่ง attach-volume
  - ใช้ตัวเลือก `–-device` เพื่อระบุจุดเมานต์
```
$ aws ec2 attach-volume –-volume-id vol-12345678 \
--instance-id i-abc1234 –-device /dev/sdf
```

=== P016
# Amazon EBS-optimized instances
- EC2 instance บางประเภทสามารถเป็นแบบ EBS-optimized ได้
  - ให้การเชื่อมต่อเครือข่ายเฉพาะ (dedicated) ไปยัง EBS volume
  - เพิ่มสมรรถนะ I/O ของ Amazon EBS
- สำหรับ instance types แบบ EBS-optimized การปรับให้เหมาะสมจะเปิดอยู่โดยค่าเริ่มต้น
- สำหรับ instance types อื่นที่รองรับ ต้องเปิดการปรับให้เหมาะสมเอง
- ได้สมรรถนะเพิ่มขึ้นหากใช้ instance type ที่อิงกับ Amazon EC2 Nitro System
แผนภาพ (AWS Cloud → Region → Availability zone → VM host computer): instance แบบ "Standard" เชื่อมกับ Amazon EBS Volume 1 ผ่านเครือข่ายทั่วไป; EBS-optimized instance เชื่อมกับ Amazon EBS Volume 2 ผ่านการเชื่อมต่อเครือข่ายเฉพาะ (Dedicated network connection)

=== P017
# Amazon EBS incremental snapshots (snapshot แบบเพิ่มส่วน)
แผนภาพ: ข้อมูลของ EBS volume (EBS volume data) ถูกถ่าย snapshot ไปเก็บเป็นข้อมูล EBS snapshot ใน Amazon S3 (EBS snapshot data in Amazon S3) โดยเก็บเฉพาะบล็อกที่เปลี่ยนแปลง:
- Snapshot 1 = ABC (เก็บบล็อก A, B, C)
- Snapshot 2 = ABCDEF (เก็บเพิ่มเฉพาะ D, E, F)
- Snapshot 3 = GHCDEF (เก็บเพิ่มเฉพาะ G, H ที่เปลี่ยนแทน A, B)

=== P018
# สร้าง snapshot ของ EBS volume
- ใช้คำสั่ง AWS CLI create-snapshot คำสั่งนี้ทำงานแบบอะซิงโครนัส (returns asynchronously)
- พิจารณาหยุด instance หรือยกเลิกการเมานต์ volume ก่อน:
  - เพื่อความครบถ้วน (มิฉะนั้นการเขียนที่เกิดภายหลังจะไม่ถูกบันทึก)
  - แนะนำอย่างยิ่งสำหรับ volume ที่ทำหน้าที่เป็น root device
  - สำคัญมากสำหรับเซิร์ฟเวอร์ฐานข้อมูลและการตั้งค่า Redundant Array of Independent Disks (RAID)
```
aws ec2 create-snapshot –-volume-id vol-1234567890abcdef0
--description "This is my root volume snapshot"
```

=== P019
# คัดลอก snapshot และพิสูจน์การคัดลอก
- ใช้คำสั่ง AWS CLI copy-snapshot
- ข้อมูลระหว่างส่ง (in transit) ถูกเข้ารหัสโดยอัตโนมัติ
- snapshot ใหม่มี ID ต่างจากต้นฉบับ
คำสั่ง CLI: คัดลอก snapshot
```
$ aws ec2 copy-snapshot –-region us-east-1 \
--source-region us-west-2 \
–-source-snapshot-id snap-1234567890abcdef0 \
--description "This is my copied snapshot"
```
คำสั่ง CLI: พิสูจน์ว่าคัดลอกไปยัง Region ใหม่แล้ว
```
$ aws ec2 describe-snapshots \
--snapshot-ids snap-0b3c2a7c2a7e4eec6 \
--region us-east-1
```

=== P020
# กู้คืน snapshot
- snapshot ถูกเก็บใน Amazon S3 แต่เข้าถึงโดยตรงไม่ได้ AWS เป็นผู้จัดการ
- ค้นหา snapshot ID แล้วกู้คืนเป็น volume ใหม่ด้วยคำสั่ง create-volume
- volume ที่กู้คืนจาก snapshot จะมีความล่าช้าในการเข้าถึงครั้งแรก (first-access penalty) ควรพิจารณาอ่านทุกบล็อกก่อนเพื่อขจัดความล่าช้านี้ในระบบ production
คำสั่ง CLI (ต้นฉบับเขียนหัวว่า "Copy a snapshot" แต่คำสั่งคือการกู้คืน):
```
$ aws ec2 create-volume \
–-size 80 \
–-availability-zone us-east-1a \
--volume-type gp2 \
–-snapshot-id snap-1234567890abcdef0
```

=== P021
# กู้คืน snapshot
- snapshot ถูกเก็บใน Amazon S3 แต่เข้าถึงโดยตรงไม่ได้ AWS เป็นผู้จัดการ
- ค้นหา snapshot ID แล้วกู้คืนเป็น volume ใหม่ด้วยคำสั่ง create-volume
- volume ที่กู้คืนจาก snapshot จะมีความล่าช้าในการเข้าถึงครั้งแรก ควรพิจารณาอ่านทุกบล็อกก่อนเพื่อขจัดความล่าช้านี้ในระบบ production
คำสั่ง CLI (ต้นฉบับเขียนหัวว่า "Proof of copy to a new Region" – ใช้ตรวจสถานะ volume ที่กู้คืน):
```
$ aws ec2 \
describe-volume-status \
--volume-ids vol-0c108c43c627cb26d
```

=== P022
# การจัดการวงจรชีวิตของ snapshots
- ใช้ **Amazon Data Lifecycle Manager** (Amazon DLM) เพื่อทำให้การสร้าง การเก็บรักษา และการลบ snapshots เป็นอัตโนมัติ
- Amazon DLM ใช้ tags เพื่อระบุ EBS volumes ที่จะสำรองข้อมูล
- กำหนดการสำรองข้อมูลและการเก็บรักษาที่ต้องการให้ Amazon DLM ใน lifecycle policy ประกอบด้วย:
  - ประเภททรัพยากร (Resource type)
  - tag เป้าหมาย (Target tag)
  - ตารางเวลา (Schedule)

=== P023
# การจัดการ EC2 snapshot ด้วย Amazon DLM
คำสั่ง AWS CLI สำหรับการจัดการ EC2 snapshot ด้วย Amazon DLM:
```
$ aws dlm create-default-role
```

=== P024
# จัดการ EBS volumes ด้วย lifecycle policy
สร้าง **lifecycle policy** เพื่อจัดการการสำรองข้อมูลของ EBS volumes ต้องสร้างไฟล์ JSON ที่ครอบคลุมรายละเอียดของ policy
- สร้าง lifecycle policy เพื่อจัดการการสำรองข้อมูลของ EBS volumes
- สร้างไฟล์ JSON ก่อนสร้าง policy เพื่อกำหนดรายละเอียดของ policy

=== P025
# จัดการ EBS volumes ด้วย lifecycle policy
คำสั่งสำหรับสร้าง lifecycle policy:
```
$ aws dlm create-lifecycle-policy \
--description "My backup policy" \
--state ENABLED \
--execution-role-arn\
arn:aws:iam::197757065544:role/AWSDataLifecycleManagerDefaultRole \
--policy-details file://policyDetails.json
```

=== P028
# Instance store
นิยามของ instance store:
- พื้นที่จัดเก็บระดับบล็อกที่ไม่คงอยู่ถาวร (non-persistent) บนระบบดิสก์ที่ใช้ร่วมกัน
- รวดเร็ว
- ถูกเรียกคืนเมื่อ instance ถูก terminate
- ให้มาฟรีกับ instances บางประเภท
กรณีการใช้งาน:
- บัฟเฟอร์ (Buffers)
- แคช (Cache)
- ข้อมูลชั่วคราว (Scratch data)
แผนภาพ: VM host computer ใน AWS มี Instance store ที่แบ่งเป็นพื้นที่ชั่วคราว (Ephemeral) ให้ Instance 1 และ Instance 2

=== P029
# Instance store volumes
- instance store มีให้กับ instance types หลายประเภทแต่ไม่ใช่ทั้งหมด
- จำนวน ขนาด และประเภท (HDD เทียบกับ SSD) แตกต่างกันตาม instance type:
  - instance stores ที่ใช้ NVMe มีสมรรถนะ I/O สูงกว่า
- การเมานต์:
  - ต้องเมานต์ instance store ก่อนจึงจะเข้าถึงได้
  - บน Windows ถูกเมานต์อัตโนมัติโดยบริการ EC2Launch
  - บน Linux โดยทั่วไปต้องเมานต์เอง

=== P030
# ประเด็นสำคัญ (Key Takeaways)
- instance store คือพื้นที่จัดเก็บแบบบล็อกชั่วคราวที่ต่อกับ instance ทางกายภาพ ซึ่ง instance นั้นอยู่บนโฮสต์จริง
- ใช้ instance store เก็บข้อมูลที่ไม่จำเป็นต้องเก็บไว้เกินอายุของ instance
