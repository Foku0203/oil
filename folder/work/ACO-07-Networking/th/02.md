=== P031
# สถานะระหว่างการสร้างการเชื่อมต่อ VPC peering
สถานะระหว่างการสร้างการเชื่อมต่อ VPC peering ได้แก่:
Initiating-request (กำลังส่งคำขอ) → Pending-acceptance (รอการยอมรับ) → [Request accepted – คำขอได้รับการยอมรับ] → Provisioning (กำลังจัดเตรียม) → Active (ใช้งานได้)

=== P032
# ข้อจำกัดของ VPC peering
ข้อจำกัดของ VPC peering ได้แก่:
- ช่วง IP address ต้องไม่ทับซ้อนกัน
- ไม่มี transitive peering (การส่งต่อผ่าน VPC ตัวกลาง), edge routing หรือการเข้าถึง internet gateway
- ไม่มีการ route ผ่าน NAT ระหว่าง VPC
- ไม่มีการแปลง DNS lookup ของ private IP addresses
- รองรับการอ้างอิง security groups ข้าม Regions
แผนภาพ: VPC A (172.16.0.0/16) peering กับ VPC B (10.0.0.0/16) และ VPC A peering กับ VPC C (192.168.0.0/16) แต่ระหว่าง VPC B กับ VPC C ไม่มี transitive peering (No transitive peering)

=== P033
# AWS site-to-site VPN
แผนภาพ: Region → VPC (10.0.0.0/16) → Availability Zone A มี VPN-only subnet 10.0.0.0/24 ที่มี Instances (10.0.0.5, 10.0.0.6, 10.0.0.7) ผ่าน Router → VPN gateway → VPN Connection → Customer gateway → ศูนย์ข้อมูลองค์กร (Corporate data center 192.168.10.0/24); มี Availability Zone B ด้วย

=== P034
# AWS Direct Connect plus VPN
แผนภาพ: ศูนย์ข้อมูลองค์กร (Corporate data center) → Router → การเชื่อมต่อ Ethernet และ VPN (WAN) → AWS Direct Connect location (AWS Direct Connect) → Private virtual interface → VPN gateway → VPC (EC2 instance) ใน AWS Cloud

=== P035
# AWS VPN CloudHub
แผนภาพ: VPC ที่มี VPN gateway เดียว และ subnets ใน Availability Zone A (VPC subnet 1 มี Instances) และ Availability Zone B (VPC subnet 2 มี Instances) เชื่อม VPN connection ไปยังเครือข่ายลูกค้า 3 แห่ง:
- Customer Gateway ASN: 6500 – Customer network New York
- Customer Gateway ASN: 6501 – Customer network Los Angeles
- Customer Gateway ASN: 6502 – Customer network Miami

=== P036
# ตัวเลือกการเชื่อมต่อ VPN
แผนภาพ: AWS Cloud → VPC (EC2 instance) → VPN Gateway
- AWS Direct Connect plus VPN: ศูนย์ข้อมูลองค์กร New York → Router → การเชื่อมต่อ Ethernet (WAN)
- AWS VPN CloudHub: ศูนย์ข้อมูลองค์กร Los Angeles และ Miami → Customer gateway → VPN connection ผ่านอินเทอร์เน็ต (VPN connection via internet)

=== P037
# VPC endpoints
แผนภาพ (AWS Cloud):
- Service consumer VPC: Instance ใน Subnet → Interface endpoint (elastic network interface) → AWS PrivateLink → VPC endpoint service ใน Service provider VPC
- Router → Gateway endpoint → Amazon Simple Storage Service (Amazon S3)
- Router → Gateway endpoint → Amazon DynamoDB

=== P038
# AWS PrivateLink interface endpoint
แผนภาพ (AWS Cloud): Service consumer VPC มี Instance และ Interface endpoints (elastic network interface) หลายตัว แต่ละตัวเชื่อมผ่าน AWS PrivateLink ไปยัง:
- VPC endpoint service ใน Service provider VPC (Network load balancer → Instances)
- บริการใน AWS Marketplace (AWS Marketplace service)
- บริการของ AWS (AWS service)

=== P040
# AWS Transit Gateway
AWS Transit Gateway เป็น gateway เดียวที่เชื่อมต่อ VPC และเครือข่าย on-premises ได้หลายพันเครือข่าย:
- ต่อเข้ากับ VPCs และ VPNs
- รองรับการกระจายเส้นทาง (route propagation) จาก route tables ของ VPCs และการเชื่อมต่อ VPN ที่ต่ออยู่
แผนภาพ: AWS Transit Gateway อยู่ตรงกลาง เชื่อมกับ VPC (Instances) สองตัว และศูนย์ข้อมูลองค์กร (Servers) ผ่าน VPN connection

=== P041
# โมดูล 7: เครือข่าย
การรักษาความปลอดภัยของเครือข่าย (Securing your network)

=== P042
# การป้องกันเครือข่ายแบบหลายชั้นสำหรับ VPC (Layered network defense)
ชั้นการป้องกันจากนอกเข้าใน (VPC → OS):
- 1: VPC route tables
- 2: Subnet ACLs: ขาเข้า (Inbound) หรือขาออก (outbound)
- 3: Security groups ของ EC2 หรือ elastic network interface
- 4: การป้องกันระดับโฮสต์ของบุคคลที่สาม (Third-party, host-based protection)

=== P043
# Security groups
Security groups:
- ใช้อนุญาตทราฟฟิกเข้าหรือออกจาก elastic network interface
- ค่าเริ่มต้นถูกตั้งไว้ให้:
  - **ปฏิเสธ (Deny)** ทราฟฟิกขาเข้าทั้งหมด
  - **อนุญาต (Allow)** ทราฟฟิกขาออกทั้งหมด
- **Stateful (จำสถานะ):** หากกฎอนุญาตให้ทราฟฟิกไหลในทิศทางหนึ่ง การตอบกลับจะไหลในทิศทางตรงข้ามได้โดยอัตโนมัติ
- มักดูแลโดยนักพัฒนาแอปพลิเคชัน
ตัวอย่าง mompopcafe security group – Outbound Rules:
| Type | Protocol | Port Range | Source |
| All traffic | All | All | 0.0.0.0/0 |
Inbound Rules:
| Type | Protocol | Port Range | Source |
| HTTP | TCP | 80 | 0.0.0.0/0 |
| SSH | TCP | 22 | 0.0.0.0/0 |
| MYSQL/Aurora | TCP | 3306 | 0.0.0.0/0 |

=== P044
# Network access control lists (network ACL)
Network access control lists (network ACL):
- อนุญาตหรือปฏิเสธทราฟฟิกเข้าและออกจาก subnets
- Network ACL ค่าเริ่มต้น:
  - **อนุญาต (Allows)** ทราฟฟิกขาเข้าและขาออกทั้งหมด
- **Stateless (ไม่จำสถานะ):** แม้กฎจะอนุญาตให้ทราฟฟิกไหลในทิศทางหนึ่ง คุณต้องอนุญาตการตอบกลับในทิศทางตรงข้ามอย่างชัดแจ้ง
- เพิ่มความแข็งแกร่งของความปลอดภัยในฐานะการป้องกันชั้นรองที่ระดับ subnet
Inbound Rules ของ Default Network ACL:
| Rule # | Type | Protocol | Port Range | Source | Allow or Deny |
| 100 | ALL Traffic | ALL | 80 | 0.0.0.0/0 | ALLOW |
| * | SSH | TCP | 22 | 0.0.0.0/0 | DENY |

=== P045
# Bastion host
bastion host:
- ให้การเข้าถึงจาก public subnet ไปยัง private subnet
- เป็นจุดกระโดด (jump point) เพื่อเข้าถึง private subnet
- อย่าเก็บ private keys ไว้
- สำหรับ Linux instances ให้ใช้คุณสมบัติ agent forwarding ของ SSH client เพื่อระบุคีย์
- สำหรับ Windows instances ให้ถอดรหัสรหัสผ่านด้วยคีย์ในคอนโซล Amazon EC2 แล้วเพิ่ม instance เข้า domain
แผนภาพ: ไคลเอนต์คอมพิวเตอร์ในเครื่อง (SSH สำหรับ Linux, RDP สำหรับ Windows) → Bastion host ใน Public subnet (มี NAT) → ล็อกอินเข้า private instance ผ่าน bastion (Log in to private instance via bastion) → Private instance ใน Private subnet (แต่ละตัวมี Security group)

กฎของ security group ของ private instance:
| Protocol | Source |
| 22 (SSH) | sg-192d536a |

=== P047
# Remote desktop gateway ในฐานะ Windows bastion host
แผนภาพ: HTTPS client ที่ได้รับอนุญาตให้เข้าถึง Remote Desktop gateway → TCP port 443 → Remote Desktop gateway bastion 10.50.1.29 (Security group sg-192d536a) ใน Public subnet 10.50.1.0/24 → ส่งต่อคำขอ RDP (Forward RDP request) ทาง TCP port 3389 → Private instance 10.50.2.191 ใน Private subnet 10.50.2.0/24

| Protocol | Source |
| 443 (SSL) | 0.0.0.0/0 |
กฎของ security group ของ private instance:
| Protocol | Source |
| 3389 (RDP) | sg-192d536a |

=== P048
# โมดูล 7: เครือข่าย
การแก้ไขปัญหาเครือข่ายบน AWS (Troubleshooting networks on AWS)

=== P049
# งานแก้ไขปัญหาที่พบบ่อย
- 1. ตรวจสอบว่า instance เปิดและทำงานอยู่
  - ตรวจว่าผ่านทั้ง System Status check และ Instance Status check
- 2. ตรวจสอบว่า security groups ที่ผูกกับ instance อนุญาตการเชื่อมต่อสำหรับโปรโตคอลและพอร์ตที่ต้องการ
- 3. ตรวจสอบว่า network ACLs ที่ผูกกับ subnet อนุญาตทราฟฟิกจากพอร์ตและโปรโตคอลที่จำเป็น
- 4. ตรวจสอบว่า route table ที่ผูกกับ subnet มีกฎปลายทาง (destination rules) ที่ชี้ไปยังเป้าหมาย (targets) ที่เหมาะสม

=== P050
# การแก้ไขปัญหาการเชื่อมต่อ instance
งานแก้ไขปัญหาที่พบบ่อย:
- ตรวจสอบว่า instance กำลังทำงาน
- ตรวจสอบกฎของ security groups
- ตรวจสอบกฎของ network ACL
- ตรวจสอบกฎของ route table
หากคุณเชื่อมต่อ instance ผ่านอินเทอร์เน็ตไม่ได้:
- ตรวจสอบว่า public IP address หรือชื่อ DNS ที่ใช้ถูกต้อง
- ตรวจสอบว่า instance มี public IP address หรือ Elastic IP address
- ตรวจสอบว่ามี internet gateway ต่อกับ VPC ของ instance
- ตรวจสอบว่า route table ของ subnet ของ instance มีกฎเส้นทางสำหรับปลายทาง 0.0.0.0/0 ผ่าน internet gateway

=== P051
# การแก้ไขปัญหาการเชื่อมต่อ SSH
งานแก้ไขปัญหาที่พบบ่อย:
- ตรวจสอบว่า instance กำลังทำงาน
- ตรวจสอบว่าพอร์ต 22 เปิดใน security group
- ตรวจสอบกฎของ network ACL
- ตรวจสอบกฎของ route table
หากคุณเชื่อมต่อ instance ด้วย SSH ไม่ได้:
- ตรวจสอบข้อมูลรับรองการเชื่อมต่อ instance:
  - ชื่อผู้ใช้ (User name)
  - private key ของ instance

=== P052
# การแก้ไขปัญหา NAT
งานแก้ไขปัญหาที่พบบ่อย:
- ตรวจสอบว่า instance กำลังทำงาน
- ตรวจสอบกฎของ security groups
- ตรวจสอบกฎของ network ACL
- ตรวจสอบกฎของ route table
หากการตั้งค่า NAT ไม่ทำงาน:
- NAT instance หรือ NAT gateway:
  - ตรวจสอบว่า route table มีเส้นทางไปยัง NAT instance หรือ NAT gateway
- NAT instance:
  - ตรวจสอบว่าปิด Source/Dest Check แล้ว
  - รีสตาร์ต NAT instance
  - ตรวจสอบกฎขาเข้าของ security group
