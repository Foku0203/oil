# การประมวลผลแบบ Serverless (Serverless computing)
| การ deploy และปฏิบัติการแบบดั้งเดิม (Traditional) | การ deploy และปฏิบัติการแบบ Serverless |

| อัปเดตระบบปฏิบัติการ (OS) | ไม่ต้องทำ (AWS ดูแล) |
| ติดตั้งแพลตฟอร์มแอปพลิเคชัน | ไม่ต้องทำ (AWS ดูแล) |
| **สร้างและ deploy แอปพลิเคชัน** | **สร้างและ deploy แอปพลิเคชัน** |
| ตั้งค่าการขยายขนาดอัตโนมัติและการกระจายโหลด | ไม่ต้องทำ (AWS ดูแล) |
| ติดตั้งแพตช์ รักษาความปลอดภัย และเฝ้าติดตามเซิร์ฟเวอร์เป็นประจำ | ไม่ต้องทำ (AWS ดูแล – ในสไลด์คือ "Continuously patch, secure, and monitor servers" ที่ทำเป็นสีจาง) |
| **เฝ้าติดตามและดูแลแอปพลิเคชัน** | **เฝ้าติดตามและดูแลแอปพลิเคชัน** |
(ในสไลด์ ฝั่ง Serverless แสดงรายการที่ผู้ใช้ไม่ต้องทำเป็นตัวอักษรสีจาง เหลือเพียง "Build and deploy applications" และ "Monitor and maintain applications" ที่ผู้ใช้ยังต้องทำ)

=== P007
# AWS Lambda
AWS Lambda ช่วยให้โค้ดทำงานได้โดยไม่ต้องจัดเตรียมหรือจัดการเซิร์ฟเวอร์
- 1. อัปโหลดโค้ดของคุณขึ้น AWS Lambda (เป็น Lambda function)
- 2. ตั้งค่าให้โค้ดถูกทริกเกอร์จากบริการ AWS อื่น ๆ (AWS SERVICES), HTTP endpoints (HTTP ENDPOINTS) หรือกิจกรรมในแอปพลิเคชัน (MOBILE APPS)
- 3. AWS Lambda รันโค้ดของคุณเฉพาะเมื่อถูกทริกเกอร์เท่านั้น
- 4. จ่ายตามเวลาประมวลผล (compute time) ที่ใช้

=== P008
# คุณสมบัติหลักของ AWS Lambda
คุณสมบัติหลักของ AWS Lambda ได้แก่:
- นำโค้ดของคุณเองมาใช้ (Bring your own code)
- การดูแลระบบเป็นอัตโนมัติทั้งหมด (Completely automated administration)
- ทนทานต่อความผิดพลาดในตัว (Built-in fault tolerance)
- ขยายขนาดอัตโนมัติ (Automatic scaling)
- ประสานการทำงานของหลาย function (Orchestrate multiple functions)
- โมเดลความปลอดภัยแบบผสานรวม (Integrated security model)
- จ่ายตามการใช้งาน (Pay per use)
- โมเดลทรัพยากรที่ยืดหยุ่น (Flexible resource model)

=== P009
# ขั้นตอนการ deploy AWS Lambda
- #1 สร้างคลาส Lambda handler ในโค้ดของคุณ
- #2 สร้าง AWS Lambda function
- #3 อนุญาตให้ AWS Lambda รับบทบาท (assume) IAM role
- #4 อัปโหลดโค้ด
- #5 เรียกใช้ (invoke) AWS Lambda function
- #6 เฝ้าติดตาม function ของคุณ (ด้วย Amazon CloudWatch)

=== P010
# ตัวอย่าง AWS Lambda: เริ่มและหยุด Amazon EC2 instances
**หยุด instances (Stop instances):**
- ตั้งตารางเวลาให้ทริกเกอร์ AWS Lambda หยุด instances ตอนกลางคืน
- AWS Lambda function (ที่มี Role) ถูกทริกเกอร์ให้หยุด EC2 instances
- Amazon EC2 instances เข้าสู่สถานะ stopped
**เริ่ม instances (Start instances):**
- ตั้งตารางเวลาให้ทริกเกอร์ AWS Lambda เริ่ม instances ตอนเช้า
- AWS Lambda function (ที่มี Role) ถูกทริกเกอร์ให้เริ่ม EC2 instances
- Amazon EC2 instances เข้าสู่สถานะ running

=== P011
# Lambda layers
Lambda layers ช่วยให้นักพัฒนา:
- ตั้งค่า Lambda function ให้ใช้ไลบรารีที่ไม่ได้รวมอยู่ใน deployment package
  - Lambda layer คือไฟล์ ZIP ที่มีไลบรารีและ custom runtime
- ทำให้ deployment package มีขนาดเล็ก
- หลีกเลี่ยงข้อผิดพลาดด้าน dependency ของแพ็กเกจในโค้ด
- แชร์ไลบรารีกับนักพัฒนาคนอื่น

=== P012
# ขีดจำกัดของ AWS Lambda (AWS Lambda limits)
ขีดจำกัดของ AWS Lambda ได้แก่:
- ขีดจำกัดทรัพยากรต่อการเรียกใช้แต่ละครั้ง เช่น หน่วยความจำ runtime ระยะเวลา
- ขีดจำกัดของบัญชีต่อ Region เช่น การทำงานพร้อมกัน (concurrency)
- ขีดจำกัดการ deploy เช่น ขนาดแพ็กเกจ
function ที่เกินขีดจำกัดใดก็ตามจะล้มเหลวพร้อม exception ว่าเกินขีดจำกัด (exceeded limits exception)

=== P013
# ประเด็นสำคัญ (Key Takeaway)
- การประมวลผลแบบ serverless ช่วยให้คุณสร้างและรันแอปพลิเคชันและบริการได้โดยไม่ต้องจัดเตรียมหรือจัดการเซิร์ฟเวอร์
- AWS Lambda มีความทนทานต่อความผิดพลาดและการขยายขนาดอัตโนมัติในตัว
- หน่วยความจำสูงสุดที่จัดสรรให้ Lambda function หนึ่งตัวคือ 3 GB
- เวลาทำงานสูงสุดของ Lambda function คือ 15 นาที

=== P015
# APIs
application programming interface (API):
- ให้การเข้าถึงแอปพลิเคชันผ่านโปรแกรม ตัวอย่างเช่น มักใช้กับโปรแกรมที่สื่อสารกันเอง
- รองรับหลายภาษาโปรแกรม เช่น API สำหรับ Java, API สำหรับ C++ เป็นต้น
แผนภาพ: Client → คำขอ (Request) → API interface → Application → ผลตอบกลับ (Response) → Client

=== P016
# RESTful APIs
Representational state transfer (REST):
- การสื่อสารผ่าน HTTP
- เปิดเผยทรัพยากรที่ URL เฉพาะ
- web APIs จำนวนมากเป็นแบบ RESTful
- เป็นการออกแบบสำหรับแอปพลิเคชันบนเครือข่ายที่เชื่อมโยงกันแบบหลวม (loosely coupled)
หลักการออกแบบ RESTful 6 ข้อ:
- อินเทอร์เฟซที่เป็นรูปแบบเดียวกัน (A uniform interface)
- ไม่เก็บสถานะ (Stateless)
- สถาปัตยกรรมแบบไคลเอนต์-เซิร์ฟเวอร์ (Client-server architecture)
- แคชได้ (Cacheable)
- ระบบแบบชั้น (Layered system)
- โค้ดตามต้องการ (Code on demand – ไม่บังคับ)

=== P017
# คำขอ REST (REST requests)
ส่วนประกอบของคำขอ REST ได้แก่:
- Endpoint (ในรูปของ URL)
- Method:
  - GET – เพื่ออ่านทรัพยากร
  - POST – เพื่อสร้างทรัพยากร
  - PUT – เพื่ออัปเดตทรัพยากรที่มีอยู่
  - DELETE – เพื่อลบทรัพยากร
- Header:
  - ตัวอย่าง: `-H "Content-Type: application/json"`
- Data (body):
  - โดยทั่วไปเป็นส่วนหนึ่งของคำขอ POST และ PUT
(แผนภาพ: URL, Method, Headers, Body)

=== P018
# ตัวอย่าง REST ด้วย cURL
คำขอ (Request):
```
curl –i \
–X POST \
–d @file.json \
–H "Content-Type: application/json" \
https://www.example.com/someresource/
```
ผลตอบกลับ (Response):
```
{
"Status": "Accepted"
}
```
(แผนภาพ: Client → HTTPS → API interface → Application)

=== P019
# รหัสสถานะ HTTP (HTTP status codes)
- 100s – การตอบกลับเชิงข้อมูล (Informational response)
- 200s – สำเร็จ (Success)
- 300s – การเปลี่ยนเส้นทาง (Redirection)
- 400s – ข้อผิดพลาดฝั่งไคลเอนต์ (Client errors)
- 500s – ข้อผิดพลาดฝั่งเซิร์ฟเวอร์ (Server errors)

# Amazon API Gateway
Amazon API Gateway:
- ช่วยให้นักพัฒนาสร้างและดูแล APIs ตัวอย่างเช่น สร้าง REST API ให้แอปพลิเคชันที่คุณรันบน AWS
- เป็นบริการแบบมีผู้ดูแลให้เต็มรูปแบบ (fully managed) ซึ่งจัดการ:
  - การขยายขนาด (Scaling)
  - การควบคุมการเข้าถึง (Access control)
  - การเฝ้าติดตาม (Monitoring)

=== P022
# การ deploy Amazon API Gateway
แผนภาพ: Applications หลายตัว ↔ API (Frontend) ของ Amazon API Gateway → Backend ได้แก่ AWS Lambda, Amazon DynamoDB, Amazon EC2, Amazon VPC และ Internet
บริการ AWS ประมวลผลคำขอและผลตอบกลับของการผสานรวม (AWS services processing integration requests and responses)

=== P023
# ประโยชน์ของ API Gateway
ประโยชน์ของ API Gateway ได้แก่:
- ได้ประโยชน์จากต้นทุนต่ำและประสิทธิภาพ
- ให้สมรรถนะได้ทุกระดับขนาด
- เฝ้าติดตามกิจกรรมของ API ได้ง่าย
- ทำให้การพัฒนา API คล่องตัวขึ้น
- ใช้การควบคุมความปลอดภัยที่ยืดหยุ่น
- รัน APIs โดยไม่ต้องมีเซิร์ฟเวอร์
- สร้าง RESTful API endpoints ให้บริการที่มีอยู่

=== P024
# ตัวอย่าง API Gateway (1 จาก 2)
แผนภาพ Serverless Web Application (Client เชื่อมต่อกับส่วนต่าง ๆ):
- **Amazon Simple Storage Service (S3)** – พื้นที่จัดเก็บแบบออบเจกต์และการโฮสต์เว็บไซต์: Amazon S3 โฮสต์เนื้อหาเว็บไซต์แบบสแตติก เช่น HTML, CSS, JavaScript
- **Amazon Cognito** – ไดเรกทอรีผู้ใช้และการยืนยันตัวตน: Amazon Cognito ลงทะเบียนและยืนยันตัวตนผู้ใช้ใหม่ของแอปพลิเคชัน
- **Amazon API Gateway** (RESTful API) → **AWS Lambda** (การประมวลผลแบบ serverless) → **Amazon DynamoDB** (ฐานข้อมูล NoSQL): ระบบหลังบ้านแบบ serverless ของแอปพลิเคชันรับการเรียก API แบบไดนามิกและประมวลผลตรรกะทางธุรกิจ

=== P029
# Docker
Docker คือ:
- แพลตฟอร์มซอฟต์แวร์ที่ช่วยให้คุณสร้าง ทดสอบ และ deploy แอปพลิเคชันได้อย่างรวดเร็ว
- ใช้บรรจุซอฟต์แวร์เป็นหน่วยมาตรฐานที่เรียกว่าคอนเทนเนอร์
คอนเทนเนอร์มีทุกอย่างที่ซอฟต์แวร์ต้องใช้ในการทำงาน: ไลบรารี (Libraries), เครื่องมือระบบ (System tools), โค้ด (Code), Runtime

=== P030
# ตัวอย่างการ deploy ด้วย Docker
**ซ้าย:** ระบบปฏิบัติการโฮสต์เดียวที่ติดตั้ง Docker และวิธีที่ Docker ทำงาน**บน on-premises**
- ชั้นจากบนลงล่าง: Application A / B / C → Bins/Libs ของแต่ละแอป → Docker → Host OS → Infrastructure
**ขวา:** สี่แอปพลิเคชันโฮสต์บนระบบปฏิบัติการ guest สามตัว และวิธีที่ทำงาน**บน AWS**
- Guest OS #1 + Docker: Application A และ B (แต่ละตัวมี Bins/Libs)
- Guest OS #2 + Docker: Application C (มี Bins/Libs)
- Guest OS #3: Application D (มี Bins/Libs, ไม่ใช้ Docker)
- ทั้งหมดอยู่บน Hypervisor → Infrastructure
