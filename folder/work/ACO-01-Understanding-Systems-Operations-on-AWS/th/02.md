=== S013
# ขอบเขต (Scope) ของบริการ Amazon Web Services
**Global (ระดับโลก)**
- IAM users, groups และ roles
- Amazon Route 53 hosted zones และ record sets
- Amazon CloudFront distributions
**Region (ระดับภูมิภาค)**
- Amazon Simple Storage Service (Amazon S3) buckets
- Amazon Machine Images (AMIs)
- Amazon CloudWatch metrics
- Amazon Elastic Block Store (Amazon EBS) snapshots
- Amazon ElastiCache clusters
- Amazon Virtual Private Cloud (VPC)
**Availability Zone (ระดับ Availability Zone)**
- Amazon EC2 instances
- Amazon EBS volumes
- Amazon Relational Database Service (Amazon RDS) database instances
- Subnets
--- notes
คุณสมบัติบางอย่างของบริการ AWS เป็นระดับ Region บางอย่างเป็นระดับโลก (global) และบางอย่างมีอยู่เฉพาะใน Availability Zone ที่สร้างขึ้นเท่านั้น การเข้าใจขอบเขตของคุณสมบัติต่าง ๆ จึงสำคัญ
ตัวอย่างเช่น เมื่อผู้ใช้กำหนด S3 bucket จะต้องระบุ Region ที่ bucket นั้นจะอยู่ ในทำนองเดียวกัน เมื่อจับภาพ EC2 instance เป็น AMI แล้ว AMI นั้นจะใช้ได้เฉพาะใน Region ที่จับภาพเท่านั้น หากผู้ใช้ต้องการสร้าง instance จาก AMI นั้นใน Region อื่น ต้องคัดลอก AMI ไปยัง Region นั้นก่อน AWS CloudWatch metrics, Amazon Block Store (Amazon EBS) snapshots, Amazon ElastiCache clusters และ VPC ก็เป็นระดับ Region ทั้งหมด (VPCs) ปัจจัยที่มีผลต่อการเลือก Region ได้แก่:
- พิจารณาค่าใช้จ่ายที่แตกต่างกันในแต่ละ Region
- พิจารณาข้อกำหนดทางกฎหมายที่เกี่ยวกับการกำกับดูแลข้อมูล (data governance)
- กฎหมายและข้อบังคับของแต่ละประเทศอาจมีผลต่อว่าข้อมูลใดข้ามพรมแดนทางภูมิศาสตร์ได้ และบริการใดที่เปิดให้ใช้
- ลดความหน่วง (latency) ด้วยการอยู่ใกล้ลูกค้าทางภูมิศาสตร์
ทรัพยากรบางอย่างเป็นระดับโลก ตัวอย่างเช่น เมื่อคุณกำหนด IAM users, groups และ roles ทรัพยากรเหล่านั้นสามารถอ้างอิงได้ในทุก Region ของบัญชี AWS hosted zones ที่กำหนดใน Amazon Route 53 ก็เป็นระดับโลกเช่นกัน รวมถึง Amazon CloudFront distributions ด้วย
คุณสมบัติบางอย่างของบริการ AWS มีอยู่เฉพาะในระดับ Availability Zone ทุก Region มี Availability Zone อย่างน้อยสองแห่ง ตัวอย่างเช่น หากผู้ใช้ launch EC2 instance ใน Region us-west-1 instance จะถูก launch ลงใน Availability Zone หนึ่ง เช่น us-west-1b หากต้องการต่อ EBS volume ใหม่เข้ากับ instance นั้น ต้องสร้าง volume ใน Availability Zone เดียวกัน (us-west-1b) มิฉะนั้นผู้ใช้จะไม่สามารถต่อ volume เข้ากับ instance นั้นได้ Subnets และ Amazon Relational Database Service (Amazon RDS) database instances เป็นตัวอย่างอื่นของออบเจกต์หรือโครงสร้างที่กำหนดอยู่ภายใน Availability Zone

=== S014
# ขีดจำกัดของบริการ (Service limits) บน AWS
จำกัดโอกาสที่จะเกิดค่าใช้จ่ายสูงเกินควร และรักษาให้เครือข่าย AWS ทำงานได้ดี
--- notes
เมื่อผู้ใช้สร้างบัญชี AWS ใหม่ จะมีการใช้ service limits ค่าเริ่มต้น บางขีดจำกัดเป็น soft limit (ขอเพิ่มได้) ตัวอย่างเช่น หากต้องการรัน EC2 instance แบบ t2.large จำนวนมากใน Region เดียวเป็น On-Demand Instances ขีดจำกัดแบบ soft ต่อ Region ของ instance ประเภทนี้คือ 20 หากพยายามรัน instance ที่ 21 ขณะที่มี 20 instance รันอยู่แล้ว จะได้รับข้อผิดพลาดเรื่องความจุ (capacity error) ผู้ใช้สามารถเปิดเคสใน AWS Support Center เพื่อขอเพิ่มขีดจำกัด (Service Limit Increase) ให้บัญชีของตน ซึ่งคำขอเหล่านี้มักได้รับอนุมัติ
นอกจากนี้ยังมี hard limit บางอย่าง ตัวอย่างเช่น API ของ Amazon Simple Notification Service (Amazon SNS) มีคุณสมบัติจำกัดอัตรา (throttling) โดยจำกัดไว้ที่ 100 รายการ Subscribe ต่อวินาที hard limit ไม่สามารถเปลี่ยนแปลงได้
รายละเอียดทั้งหมดดูได้ที่หน้าเอกสาร http://docs.aws.amazon.com/general/latest/gr/aws_service_limits.html

=== S016
# แนะนำ IAM
AWS Identity and Access Management (IAM) ช่วยให้คุณจัดการการยืนยันตัวตน (authentication) และการเข้าถึงทรัพยากร AWS ได้จากศูนย์กลาง
- เป็นคุณสมบัติของบัญชี AWS ที่ให้ใช้โดยไม่มีค่าใช้จ่าย
- สร้าง users, groups และ roles
- กำหนด policies ให้สิ่งเหล่านั้นเพื่อควบคุมการเข้าถึงทรัพยากร AWS
(ไอคอน: AWS Identity and Access Management)
--- notes
AWS Identity and Access Management (IAM) เป็นบริการที่ช่วยควบคุมการเข้าถึงทรัพยากร AWS อย่างปลอดภัย
ใช้ IAM เพื่อตั้งค่าการยืนยันตัวตน (authentication) ซึ่งเป็นขั้นแรก เพราะเป็นตัวควบคุมว่าใครเข้าถึงทรัพยากร AWS ได้โดยอิงจากการยืนยันตัวตนนั้น IAM ไม่ได้ใช้แค่ยืนยันตัวตนของผู้ใช้เท่านั้น แต่แอปพลิเคชันและบริการ AWS อื่น ๆ ก็ใช้ในการเข้าถึงด้วย
IAM ใช้ตั้งค่าการให้สิทธิ์ (authorization) กล่าวคือ เมื่อรู้ว่าผู้ใช้คือใคร ก็กำหนดได้ว่าผู้ใช้เข้าถึงทรัพยากรใดได้บ้าง และทำอะไรกับทรัพยากรเหล่านั้นได้บ้าง
IAM ทำให้ไม่ต้องแชร์รหัสผ่านหรือ access key เมื่อให้สิทธิ์การเข้าถึงแก่บุคคลหรือระบบอื่น นอกจากนี้ยังทำให้เปิดหรือปิดการเข้าถึงของผู้ใช้ได้ง่ายเมื่อเวลาผ่านไปและตามความเหมาะสม
ให้มอง IAM เป็นเครื่องมือจัดการการเข้าถึงจากศูนย์กลางว่าใคร launch, ตั้งค่า, จัดการ และ terminate ทรัพยากรได้บ้าง IAM ให้การควบคุมสิทธิ์การเข้าถึงแบบละเอียด ไม่ใช่แค่สำหรับคน แต่รวมถึงระบบหรือแอปพลิเคชันอื่นที่อาจเรียกใช้ทรัพยากร AWS อื่นผ่านโปรแกรม (programmatic calls)
- จัดการได้ไม่เพียงว่าเข้าถึงทรัพยากรใดได้ แต่รวมถึงการกระทำ (action) ใดที่ทำได้
- ตัวอย่างเช่น ใครสามารถ terminate Amazon EC2 instances ได้บ้าง?
- กำหนด credentials ที่ต้องใช้ตามบริบท เช่น:
  - ใครเข้าถึงบริการ AWS ใดได้บ้าง?
  - ผู้ใช้หรือระบบได้รับอนุญาตให้ทำอะไรกับบริการนั้นได้บ้าง?

=== S017
# IAM: การยืนยันตัวตน (Authentication)
แผนภาพ: AWS Management Console / AWS CLI / SDK → AWS Cloud → เข้าถึงบริการ AWS (Access to AWS services)
**การเข้าถึงผ่านคอนโซล (Console access):**
- ใช้ account ID หรือ alias, ชื่อ IAM user และรหัสผ่าน
- หากเปิดใช้ MFA ระบบจะถามรหัสยืนยันตัวตน (authentication code)
**การเข้าถึงผ่านโปรแกรม (Programmatic access):**
- ยืนยันตัวตนด้วย access key ID และ secret access key
- ให้สิทธิ์เข้าถึง API, AWS CLI, SDK และเครื่องมือพัฒนาอื่น ๆ
--- notes
เมื่อคุณสร้าง IAM users คุณสามารถกำหนดได้ว่าผู้ใช้จะใช้วิธีใดบ้างในการเข้าถึงบริการ AWS คุณสามารถให้การเข้าถึงผ่านโปรแกรม การเข้าถึงผ่าน AWS Management Console หรือทั้งสองแบบ
ในการให้การเข้าถึงผ่านโปรแกรม ให้สร้าง access key ID และ secret access key แล้วมอบให้ผู้ใช้ ด้วยสองสิ่งนี้ ผู้ใช้จะเข้าถึงได้:
- AWS application programming interfaces (APIs)
- AWS Command Line Interface (AWS CLI)
- AWS software development kits (SDKs)
ในการให้การเข้าถึงผ่าน AWS Management Console ให้กำหนดชื่อผู้ใช้และรหัสผ่านให้ผู้ใช้ AWS Management Console เป็นเว็บอินเทอร์เฟซที่ใช้งานง่ายสำหรับ AWS หากบัญชี IAM user เปิดใช้การยืนยันตัวตนแบบหลายปัจจัย (multi-factor authentication – MFA) ซึ่งเราแนะนำเพื่อเพิ่มความปลอดภัย ผู้ใช้จะถูกถามรหัสยืนยันเพิ่มเติมหลังจากใส่ชื่อผู้ใช้และรหัสผ่านแล้ว

=== S018
# ประเภทของ security credentials
| ประเภท | คำอธิบาย |
| Email address และรหัสผ่าน | ผูกกับบัญชี AWS (root) |
| ชื่อ IAM user และรหัสผ่าน | ใช้เข้าถึง AWS Management Console |
| Access keys | โดยทั่วไปใช้กับ AWS CLI และคำขอผ่านโปรแกรม เช่น APIs และ SDKs |
| Multi-factor authentication (MFA) | ชั้นความปลอดภัยเพิ่มเติม เปิดใช้ได้ทั้งกับบัญชี root และ IAM users |
| Key pairs | ใช้เฉพาะกับบริการ AWS บางตัว เช่น Amazon EC2 |
--- notes
ต่อไปนี้คือสรุปประเภทต่าง ๆ ของ security credentials
ทุกบัญชี AWS มี root user ที่กำหนดไว้ผ่านบัญชี root บัญชี root นี้มีอีเมลที่ผูกไว้สำหรับการกู้คืนบัญชีและการติดต่อสื่อสาร อย่างไรก็ตาม เราแนะนำว่าไม่ควรใช้ root user ทำงานประจำวัน แม้แต่งานด้านการดูแลระบบ ให้ยึดแนวปฏิบัติที่ดีที่สุด คือใช้ root user เพื่อสร้าง IAM user ก่อนเท่านั้น จากนั้นเก็บ credentials ของ root user ไว้อย่างปลอดภัย และใช้เฉพาะเมื่อต้องทำงานจัดการบัญชีและบริการเพียงไม่กี่อย่างที่ทำด้วยวิธีอื่นไม่ได้
ดังที่กล่าวในสไลด์ก่อนหน้า credentials แบบชื่อ IAM user และรหัสผ่านใช้เข้าถึง AWS Management Console หรือที่เรียกว่าคอนโซล ส่วน access keys ใช้สำหรับการเข้าถึงผ่านโปรแกรมได้เมื่อสร้างให้ผู้ใช้แล้ว
สุดท้าย เพื่อความปลอดภัยที่มากขึ้น เราแนะนำให้ใช้การยืนยันตัวตนแบบหลายปัจจัย (MFA) กับบัญชี root และกับ IAM users ทุกคนที่กำหนดไว้

# Policies และ permissions (1 จาก 2)
**ประเภทของ policy (Policy Types)** เรียงตามความถี่ในการใช้งาน (Order of Frequency of Use) จากมากไปน้อย:
| Policy Type | Permission Policies | Permission Boundaries | Managed Policies | Inline Policies |
| Identity-based | (อยู่แนวเดียวกับหัวตาราง) |  |  |  |
| Resource-based | ✓ |  |  |  |
| Organization Service Control Policy (SCP) |  | ✓ |  |  |
| Access Control Lists (ACLs) | ✓ |  |  |  |
> หมายเหตุผู้แปล: เครื่องหมาย ✓ ถอดตามตำแหน่งในภาพสไลด์ ในสไลด์แถว Identity-based อยู่แนวเดียวกับหัวคอลัมน์และไม่มีเครื่องหมาย ✓
--- notes
policy ทั้งสี่ประเภท ซึ่งบ่งบอกชนิดของสิทธิ์ที่กำหนดให้ผู้ใช้ที่ได้รับมอบหมาย เรียงตามความนิยมในการใช้งานดังนี้:
Identity-based policies ช่วยให้ผู้ใช้แนบ managed policies และ inline policies เข้ากับ IAM identities เช่น users หรือ groups ที่ users สังกัดอยู่ นอกจากนี้ยังแนบ identity-based policies เข้ากับ roles ได้ด้วย หมวดหมู่ของ policy แนบกับ IAM identities ซึ่งได้แก่:
- Users
- Groups ที่ users สังกัด
- Roles
Resource-based policies ช่วยให้ผู้ใช้แนบ inline policies เข้ากับทรัพยากร ตัวอย่างที่พบบ่อยที่สุดของ resource-based policies คือ Amazon S3 bucket policies และ IAM role trust policies โดย resource-based policies เป็นเอกสาร policy แบบ JavaScript Object Notation (JSON)
Resource-level permissions มีให้ใช้เฉพาะกับบริการและทรัพยากร AWS บางตัว และให้การควบคุมการเข้าถึงแบบละเอียดต่อออบเจกต์เฉพาะภายในบริการ AWS
- ตัวอย่างเช่น permissions policy ของ role สามารถระบุ EC2 instances และ EBS volumes เฉพาะเจาะจงได้
- Resource-level permissions ไม่ได้อนุญาตทุก action เสมอไป
- สำหรับ EC2 instances สามารถระบุ actions เช่น Reboot, Start, Stop และ Terminate ได้
- actions เช่น RunInstances ไม่สามารถระบุได้ เพราะคุณไม่รู้ InstanceID ก่อนที่การเรียก RunInstances จะเสร็จสิ้น ดังนั้น RunInstances จึงใช้กับ EC2 ในฐานะบริการทั้งหมด ไม่ใช่ทรัพยากรเฉพาะตัว
AWS Organizations service control policies (SCPs) ใช้กำหนดขอบเขตสิทธิ์ (permissions boundaries) ให้กับ AWS Organizations หรือหน่วยองค์กร (organizational units – OUs)
Access control lists (ACLs) ใช้ควบคุมได้ด้วยว่า principal ใดเข้าถึงทรัพยากรได้บ้าง ACLs คล้ายกับ resource-based policies แต่เป็น policy ประเภทเดียวที่ไม่ได้ใช้โครงสร้างเอกสาร policy แบบ JSON (ACLs ไม่ใช้โครงสร้างเอกสาร policy แบบ JSON)

# Policies และ permissions (2 จาก 2)
ตัวอย่าง IAM policy:
```
{
"Version": "2012-10-17",
"Statement": [
{
"Sid": "MFA-Access",
"Effect": "Allow",
"Action": "ec2:*",
"Resource": "*",
"Condition": {
"BoolIfExists": {
"aws:MultiFactorAuthPresent": "true"
},
"IpAddress": {
"aws:SourceIp": "1.2.3.4/32"
}
}
}
]
}
```
(policy นี้อนุญาตทุก action ของ EC2 กับทุกทรัพยากร โดยมีเงื่อนไขว่าต้องยืนยันตัวตนด้วย MFA และต้องมาจาก IP 1.2.3.4/32)
--- notes
จำไว้ว่า: policies ประเมินผลตามตรรกะต่อไปนี้:
- ยืนยันตัวตนของ principal (Authenticate principal)
- ประมวลผลบริบทของคำขอ (request context):
  - ข้อมูลสภาพแวดล้อม (Environment data)
  - ข้อมูลทรัพยากร (Resources data)
  - Actions
  - Resources
  - Principal
- ประเมิน policies ตาม:
  - ประเภทของ policy (Policy type)
  - หมวดหมู่ของ policy (Policy category)
- อนุญาตหรือปฏิเสธคำขอ (Allow or deny request)
**หมายเหตุ (NOTE):** ลำดับการประเมิน policies ไม่มีผลต่อผลลัพธ์
ตัวอย่างเช่น ผู้ใช้มี DENY แบบชัดแจ้ง (explicit DENY) ที่ผูกกับ IAM rule policy ของตน DENY นั้นจะมีผลเหนือกว่า ALLOW ใด ๆ

=== S021
# การใช้ IAM roles
แผนภาพ:
**ด้วย IAM roles ผู้ใช้สามารถให้ (Using IAM roles, a user can provide):**
- บริการ AWS ที่เข้าถึงทรัพยากร AWS อื่นได้
- การเข้าถึงแบบ single sign-on (SAML 2.0, OAuth 2.0)
**สลับ role เพื่อเข้าถึงทรัพยากรใน (Switch roles to access resources in):**
- บัญชี AWS หนึ่ง
- บัญชี AWS อื่น ๆ (การเข้าถึงข้ามบัญชี – cross-account access)
--- notes
มีสามวิธีในการใช้ role:
- ใช้แบบโต้ตอบในส่วน IAM ของ AWS Management Console
- ใช้ผ่านโปรแกรมด้วย AWS CLI
- ใช้ผ่าน AWS SDKs (การเรียก API)
แอปพลิเคชันหรือบริการ เช่น Amazon EC2 สามารถรับบทบาท (assume) role ได้ โดยขอ temporary security credentials (credentials ชั่วคราว) ของ role ซึ่งบริการนั้นใช้ส่งคำขอผ่านโปรแกรมไปยัง AWS
IAM roles ยังรองรับโซลูชัน single sign-on ด้วย ตัวอย่างเช่น ผู้ดูแล IAM สามารถตั้งค่า SAML 2.0 federation แทนการสร้าง IAM users ในบัญชี AWS เมื่อใช้ identity provider ตัวตนของผู้ใช้สามารถจัดการได้จากภายนอก AWS และตัวตนผู้ใช้ภายนอกเหล่านี้สามารถได้รับสิทธิ์ให้เข้าถึงทรัพยากรในบัญชี AWS
ข้อมูลเพิ่มเติมดูได้จากแหล่งต่อไปนี้:
- AWS Identity and Access Management: IAM Roles (Delegation and Federation): http://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html
- AWS Identity and Access Management: How Roles Differ from Resource-Based Policies: http://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_compare-resource-policies.html
- AWS Identity and Access Management: Overview of IAM Policies: http://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html

=== S022
# IAM user assume role (ผู้ใช้ IAM รับบทบาท role)
**สิทธิ์ตามผู้ใช้ (User-Based Permissions)** – เอนทิตีหนึ่ง ๆ เข้าถึงอะไรได้บ้าง?
Bob:
| ทรัพยากร | Read | Write | List |
| Resource X | ✓ | ✓ | ✓ |
Larry:
| ทรัพยากร | Read | Write | List |
| Resource Y | ✓ |  |  |
| Resource Z | ✓ |  |  |
Managers:
| ทรัพยากร | Read | Write | List |
| Resource X |  |  | ✓ |
| Resource Y |  |  | ✓ |
| Resource Z |  |  | ✓ |
**สิทธิ์ตามทรัพยากร (Resource-Based Permissions)** – ใครเข้าถึงทรัพยากรหนึ่ง ๆ ได้บ้าง?
Resource X:
| ผู้ใช้ | Read | Write | List |
| Bob | ✓ | ✓ | ✓ |
| Doug | ✓ | ✓ | ✓ |
| Jim | ✓ |  | ✓ |
| Sara |  |  | ✓ |
Resource Y:
| ผู้ใช้ | Read | Write | List |
| Bob | ✓ | ✓ | ✓ |
| Larry | ✓ |  |  |
| Sam |  | ✓ | ✓ |
--- notes
IAM users ในบัญชีสามารถรับบทบาท (assume) IAM role เพื่อใช้สิทธิ์ของ role นั้นชั่วคราวในคอนโซล ผู้ใช้จะสละสิทธิ์เดิมของตนและรับสิทธิ์ที่กำหนดให้ role แทน เมื่อผู้ใช้ออกจาก role สิทธิ์เดิมจะกลับคืนมา ผู้ใช้สามารถสลับ role เพื่อเข้าถึงทรัพยากรในบัญชี AWS หรือแม้แต่สลับ role เพื่อเข้าถึงทรัพยากรในบัญชี AWS อื่น ซึ่งเรียกว่าการเข้าถึงข้ามบัญชี (cross-account access)
cross-account access ให้สิทธิ์เข้าถึงจากบัญชี AWS อื่น ซึ่งอาจเป็นบัญชีที่คุณเป็นเจ้าของ หรือบัญชีของบุคคลอื่น หากบัญชีเป็นของบุคคลหรือองค์กรอื่น แนวปฏิบัติที่ดีคือให้ความลับร่วม (shared secret) ที่เรียกว่า external ID ด้วย ซึ่งป้องกันไม่ให้บัญชี AWS หนึ่งเดา role ARN ของอีกบัญชีแล้วส่งต่อให้บัญชี AWS ตัวกลางที่ได้รับมอบอำนาจร่วมกัน ด้วยการตั้งค่า roles ผู้ดูแล IAM สามารถให้สิทธิ์ที่จำเป็นได้โดยไม่ต้องแชร์ AWS security credentials แบบถาวร ข้อมูลเพิ่มเติมดูได้ที่ https://blogs.aws.amazon.com/security/post/Tx2Q5SSG3SFRRHO/How-to-Use-External-ID-When-Granting-Access-to-Your-AWS-Resources
role มี permissions policy ที่กำหนดว่า role ทำอะไรได้บ้างด้วย temporary security credentials เหล่านี้ สิทธิ์เหล่านี้สามารถระบุบริการ AWS และ actions ที่เกี่ยวข้อง เช่น “CreateSubnet” ในบริการ Amazon VPC นอกจากนี้ยังใช้เงื่อนไข (conditions) เพื่อกำหนดข้อจำกัดตามเวลา วันที่ IP ต้นทาง และปัจจัยอื่น ๆ ได้
AWS มี managed policies ที่แนบกับ role ได้ ขณะเดียวกันก็สามารถใช้ inline policies ได้เมื่อจำเป็น การใช้ managed policies มักทำให้การจัดการต่อเนื่องง่ายขึ้น ข้อมูลเพิ่มเติมดูได้ที่ http://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_managed-vs-inline.html
